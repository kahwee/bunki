# Actions publishing

The release guard validates stable `v<package.json version>` tags, refuses private
packages and mismatched npm lock metadata, and stops on registry errors. A 200
response means the version is immutable; it never forces another upload.

Run `node --test scripts/check-release-guard.mjs` and
`node scripts/release-check.mjs v<version>` without publishing.
`--registry` adds a read-only check of the exact public npm version.

## Approval proposal

The complete workflow is in [publish.yml](../.github/release-proposals/publish.yml).
It is outside `.github/workflows` and cannot run. After explicit approval, move it
to `.github/workflows/publish.yml` (replacing an existing publisher where present).
It uses human-pushed version tags, checks the exact tagged source against successful
CI, installs the frozen lockfile, checks/builds, packs and publishes the checked
tarball. It does not create versions, tags or GitHub releases. Stable releases use
`latest`; prereleases are excluded.

Approval must cover the workflow job's `contents: read`, `actions: read`, and
`id-token: write`, plus this npm trusted-publisher binding:

- npm package: `bunki`
- GitHub owner: `kahwee`
- repository: `bunki`
- workflow filename: `publish.yml`
- environment: blank
- allowed action: direct `npm publish` only; no extra dist-tag management grant

Use GitHub-hosted runners and npm >=11.5.1; no npm secret is needed. Configure and
read back the binding in the package owner's npm settings after approval. Existing
secret presence and a local login do not prove CI publish access. Do not revoke
existing credentials or change package security settings as part of this proposal.
See [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

No publishing action or registry trust was enabled by this change. Run the full
existing CI after review. Authentication remains untested until a separately
authorized real release; a package dry run does not validate OIDC exchange.

The existing token-based workflow now requires a matching version tag, serializes
reruns, and removes the ambiguous branch-message/force-publish paths. Its GitHub
release step still relies on existing repository token defaults; no write permission
was granted in this change. If those defaults are read-only, the GitHub release
step remains blocked until an explicitly approved job-level `contents: write` grant
or migration to the proposed GitHub-release-triggered npm workflow.

The OIDC replacement publishes stable npm `latest` on human-pushed `v*` tags, independently of the existing GitHub asset creator. A release generated by `GITHUB_TOKEN` does not trigger another release-event workflow, so release-event chaining is not relied on. It does not create GitHub releases.

Independent review confirmed the repository default GITHUB_TOKEN permission is
read-only. The existing release creator is therefore blocked. The replacement
proposal includes a separate `github-release` job, after npm publishing, with
only `contents: write`. Approval must separately cover that job-level grant.
It preserves top-level `dist` files as GitHub assets and uses checksum-based
recovery rather than clobbering. The npm job retains only read/read/OIDC access.
No grant is enabled by this PR, and no extra npm trust action is required.
